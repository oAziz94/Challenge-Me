## 4. Decision — runner `[C]`

1. **Runner.** A minimal in-repository runner owned by Foundation, TypeScript under `src/foundation/` (S1 §4.8 indicative layout), with `pg` (S1 §4.3) as its only runtime dependency. M7 is met as project-owned code: Foundation owns and maintains it; CI tests it on the pinned Node.js 24 on every change; `pg` stays on a supported release under S1 §7 rules 6–8 and the S2 §6.7 dependency report.
2. **Files.** Plain forward-only SQL files under `migrations/`, each attributed to one module schema or to Foundation (S1 §4.4 A.7). Versions are contiguous ordered integers; that is what makes gap detection enforceable. File-name syntax beyond version, attribution and slug is a task 3 implementation detail.
3. **Execution unit.** Each file is sent unchanged as one simple-protocol query over the runner's own direct session connection. The runner contains no SQL splitter and no templating.
4. **Checksums.** SHA-256 over the exact bytes of each file. Migration SQL files are pinned to LF in `.gitattributes`; CI rejects any CR character and any UTF-8 BOM in migration SQL; the runner performs no line-ending or encoding normalization.

## 6. Grants and closed schema contents `[C]`

**Grant matrix.**

| Role              | Schema `migration` | `migration.history`                     | Basis                                                        |
| ----------------- | ------------------ | --------------------------------------- | ------------------------------------------------------------ |
| `cm_migrator`     | OWNER              | OWNER — insert and one lifecycle update | DM §6.4 "owner of all schemas"                               |
| `cm_ops_readonly` | USAGE              | SELECT                                  | Its accepted DM §6.4 read role; not broadened                |
| `cm_app`          | none               | none                                    | REFERENCE ceiling narrowed to no access                      |
| `cm_queue`        | none               | none                                    | DM §6.4 "queue and admission tables only"                    |
| `cm_resolver`     | none               | none                                    | DM §6.4 [CR-3-F1] "no other role receives any privilege"     |
| PUBLIC            | none               | none                                    | This ADR                                                     |

**Catalogue assertions** (S1 §4.7; implemented in task 3): schema and table owner are `cm_migrator`; `has_schema_privilege` and `has_table_privilege` are true only for the pairs above and false for every other role and for PUBLIC, including explicit negative checks for `cm_app` SELECT and for any PUBLIC privilege; no default privileges exist on schema `migration` that would grant beyond this matrix.

**Closed contents.** Schema `migration` may contain exactly: table `history`; the constraints belonging to `history`; the indexes belonging to `history`; and, only if task 3 chooses one, one immutability/protection trigger function and its trigger on `history`. No other table, view, materialized view, function, sequence, type or other object may exist there. A catalogue assertion enumerates the namespace (`pg_class`, `pg_proc`, `pg_type`, `pg_trigger`) and fails on any object outside the permitted set.

**Migration-file static rule** (invariant specified here; the check is implemented in task 3 without a SQL parser): ordinary migration SQL may not reference schema `migration` at all — no CREATE, ALTER, DROP, GRANT, REVOKE, INSERT, UPDATE, DELETE, TRUNCATE or any other DDL or DML against it. Only the runner's own Foundation database-infrastructure code manages `migration.history`. The static SQL scan of S1 §4.8 layers 4–5 treats schema `migration` as Foundation-owned.

## 7. History-table column contract `[C]`

Minimum data contract sufficient for M8 and for classification; column types are a task 3 implementation detail within these meanings.

| Column         | Meaning                                                                                                    | Mutability                                                          |
| -------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `version`      | Contiguous ordered integer; primary key; duplicate-version detection key                                   | Immutable                                                           |
| `file_name`    | File name as applied; rename-detection key                                                                 | Immutable                                                           |
| `attribution`  | The module schema name or `foundation` the file is attributed to (S1 §4.4 A.7); never a person             | Immutable                                                           |
| `checksum`     | SHA-256 hex over the exact file bytes                                                                      | Immutable                                                           |
| `mode`         | `transactional` or `no_transaction`                                                                        | Immutable                                                           |
| `state`        | `started` or `complete`; transactional files are inserted directly as `complete`                           | `started` → `complete` only, once, by the runner                    |
| `started_at`   | Server timestamp when the row was written                                                                  | Immutable                                                           |
| `completed_at` | Server timestamp when `state` became `complete`                                                            | Set once with the transition                                        |

`applied_by` is **omitted**. The runner connects only as `cm_migrator` and asserts the connected role before writing (R10), so the column would carry nothing beyond that invariant, and any richer value — human name, email, workstation user, CI actor or login, host or OS user name, provider identity — would be a person or environment identifier. With it omitted, every column is a version number, a file name, a schema name, a hash, an enum or a server timestamp; none identifies or relates to a natural person. The row is therefore S1 operational metadata, and no purge handler or retention class applies.

## 8. Immutability and its enforcement `[C]`

Rules: `version`, `file_name`, `attribution`, `checksum`, `mode` and `started_at` never change after insert; the only lifecycle transition is `started` → `complete`, once, setting `completed_at`; rows are never deleted; no other update is permitted.

Acknowledged limit: `cm_migrator` owns and writes the table, and PostgreSQL grants cannot make an owner incapable of modifying its own table. A trigger can be disabled or dropped by the owner; a trigger is therefore defense in depth and is not claimed to bind the owner. Enforcement rests on:

1. the runner's implementation exposing only two write paths — the insert, and the single `started` → `complete` transition — with no delete and no general update path, proven by tests;
2. ordinary migration SQL being prohibited from touching schema `migration` (section 6);
3. the runner's integrity checks on every invocation (section 9);
4. integration and catalogue tests of the grant matrix, the closed contents and the lifecycle semantics;
5. optionally, a trigger as defense in depth, if task 3 chooses one.

## 9. Integrity checks and execution semantics `[C]`

**Integrity checks, all performed before any new migration is applied; any failure stops the run:** duplicate version among files; applied version with no file on disk; renamed applied file (applied `file_name` differs from the file now carrying that version); checksum mismatch between an applied row and the file; pending file with a version lower than the highest applied version; unfinished `started` record.

**Transactional migrations (default).** The runner opens a transaction, sends the file as one query, inserts the history row in state `complete`, and commits; file and record commit atomically. A transactional file must not contain explicit transaction-control statements (`BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `PREPARE TRANSACTION` or equivalents); the static check rejects them, and the runner treats a transaction that is not open after execution as failure.

**No-transaction migrations.** Exactly one SQL statement per file; the marker syntax is a task 3 implementation detail. Protocol: the runner first inserts and commits a durable history row in state `started`; it then sends the statement outside a transaction; on success it updates that row to `complete` and commits. If any later run finds a row in state `started`, it stops before applying anything, reports the version, and exits non-zero. It never retries automatically. Human resolution is required: the database is inspected, the effect is completed or reverted by hand, and the outcome is recorded through a reviewed procedure that task 3 documents.

**Repeat execution.** With no pending files and all checks passing, the runner exits zero and writes nothing; this is the idempotent re-run proof.

**Drift detection** is limited to what M2 defines (the checks above). Schema drift from out-of-band DDL is outside M1–M8 and is not claimed; the S1 §4.4 A.8 schema-only dump is a reviewer artifact produced by a separate CI step.

## 10. Hardening, logging, invocation `[C]`

- **Connection and lock.** The runner uses a direct session connection (never a pooled or transaction-mode pooled one) and holds a session-level advisory lock for the whole run, so accidental concurrent runs cannot interleave. The lock key value and namespace are an implementation detail and must not collide with application advisory locks (none exist yet; Foundation registers them when they do).
- **Logging.** Logs and errors carry the file version and name, timings and database error codes; never SQL text, parameter values or migrated data (R16).
- **CI.** One `pnpm` script, run against the job-local PostgreSQL 18 container with a credential that exists only inside the job (R17). Sequence: container superuser bootstrap (roles; schema `migration` with `AUTHORIZATION cm_migrator`; the grants of section 6), migrate as `cm_migrator`, migrate again expecting no change, catalogue assertions, schema-only dump artifact (R5, R7).
- **Local development.** The same script against the S1 §4.10 Docker Compose database, credential read from the untracked `.env.local`.
- **Production.** The fourth image command of S1 §4.12 runs the same code; the `cm_migrator` credential is supplied to that command only.

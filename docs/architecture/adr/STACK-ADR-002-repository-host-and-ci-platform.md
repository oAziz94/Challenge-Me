## 6. Decision proposed

**Decision `[C]`, within the direction of section 3 (drafted as a proposal; accepted 2026-10-06, section 14).** GitHub as the repository host — a **public** repository owned by the engineering authority's **personal account on the free plan** — and GitHub Actions as the CI platform on GitHub-hosted Linux runners.

**Why it fits.** Every Foundation control for tasks 1 and 2 can be configured on the free plan for a public repository (6.1); hosted runners are free for public repositories, which removes the main cost of container-based integration tests; and every check is a job that does not depend on a paid platform product.

**Why GitLab was not proposed.** On its free tier the monthly compute allowance is limited, Testcontainers needs additional privileged configuration, and the path and secret controls that would add defense in depth are in paid tiers. It would still satisfy the contract.

### 6.2 Remote access, merge authority and the limit of platform enforcement

**Remote-access model `[E16]`.** Claude, Codex and other development tools may, when explicitly instructed, use the engineering authority's GitHub credentials under his account to push and update non-protected branches, create pull requests, and read pull-request and check status. They may also run the local `git commit` command (E17). No separate OS account, machine, credential isolation, non-persistent authentication or removal of cached credentials is required.

**What tools must not do `[E16]`.** Independently merge a pull request into `main`; bypass or disable branch protection; weaken a required check; change repository protection or settings without the engineering authority's explicit instruction. The governance rule behind this is AGENTS §3 item 17a: merging is a human action.

**The boundary, stated honestly.** The boundary is **not** "tools cannot push". It is: _tools may prepare and publish candidate changes; only the engineering authority decides whether a change is merged into protected `main`._ GitHub cannot distinguish the engineering authority from an AI process when both operate under the same account and credential. Therefore:

- the account identity on a branch push does not prove that the engineering authority personally performed it. For candidate branches that is acceptable;
- the same is true of a merge: the platform records the account, not the person or process behind it. The control that merging is a human decision is the engineering authority's own pull-request review and merge decision under the project's governance rules (AGENTS §3 item 17a; AIW §2, §10), together with the standing prohibition on tools performing that action. This ADR does not claim that the platform enforces it, and does not claim any credential separation that does not exist;
- branch protection can be made to apply to administrators, but the owner can still change or remove the rule. Any such change by a tool without explicit instruction is a governance breach, not something the platform prevents.

**Main-branch protection requirement `[C]`, to the extent the public / personal / free baseline provides it:**

1. `main` requires a pull request; direct pushes to `main` are rejected.
2. Required CI and security checks must pass before merge, with the branch up to date.
3. Force pushes to `main` are disabled.
4. Deletion of `main` is disabled.
5. The protections apply to the repository owner and administrators where the platform supports that control.
6. No required approving review (E2); no required code-owner review (6.3).

What the platform does enforce under this configuration: no change reaches `main` except through a pull request whose required checks have passed. What it does not enforce: who, or what process, opened or merged that pull request.

**Supporting controls.** CI workflows receive a read-only token and can neither merge nor change settings (6.4). The local harness restrictions (`.claude/settings.json`: confirmation on `git push`, denial of destructive Git commands) remain as defense in depth.

### 6.3 Authoritative-path governance with one human authority

- **Default: blocked.** A required check fails any pull request whose diff touches `docs/specifications/authoritative/**` (FB §16 row 1; AGENTS §3.3).
- **Authorized route (E4).** The check passes for such a pull request only when the same change set carries the evidence that change control itself requires (16 §6.7): a change record under `docs/decisions/` naming the affected origin tags; the artifact revision bump and header revision note; and the corresponding Reconciliation Report entries (the §2.2 matrix row and the §7 register row). The check verifies that this evidence is present and mutually consistent. There is no label, commit-message keyword or other marker that switches the check off.
- **What the check proves and what it does not.** It proves that an authoritative-path change is accompanied by the governance evidence, which stops accidental or unaccompanied edits. It does **not** prove who wrote that evidence: under one identity (E3) the platform cannot distinguish a human-authored change record from an agent-drafted one. Authorization is therefore the engineering authority's own act — reviewing the pull request and merging it (E2, E4) — together with the standing rules that agents never edit the authoritative path (AGENTS §3.3; local deny rules) and that only a human writes an approval state (AIW §10).
- **Relation to the brief (E11).** FB §16 row 1 describes the proof as "branch protection + path protection; CI check that no diff touches" the path. The engineering authority's determination is that the governance-evidenced route is the _implementation_ of that protection, not a weakening or bypass of it, and that the brief is not amended at this point. The reading behind the determination: the brief's source for the row is AGENTS §3.3 (agents never edit the authoritative path), while the contract itself provides for human-authorized revision through change control (16 §6.7; CLAUDE.md §3); a check that blocks every change except one carrying that change-control evidence protects the path against exactly what the brief protects it against. The drafting agent notes that this is not the row's literal wording. **The independent reviewer must explicitly verify that the interpretation is compatible with the approved brief. If the reviewer finds a conflict with FB §16, this ADR is not accepted until the brief is amended through its governance process** (section 14).
- **Governance and CI files.** `CLAUDE.md`, `AGENTS.md`, `docs/engineering/`, `.claude/`, `docs/decisions/`, `docs/architecture/` and `.github/` have no platform-enforced reviewer on this baseline. A required check reports when a pull request touches them, so that the engineering authority sees it before merging. A CODEOWNERS file may be kept as documentation of ownership; it enforces nothing here.

**Self-modifying changes: the limit of CI as evidence (review finding F2).** Pull-request workflows execute the workflow and script definitions from the pull request's own ref. A pull request can therefore change the very check that judges it. CI output alone is **not** an authoritative review signal when the pull request changes any of: `.github/**`; the governance and path-check scripts; `docs/specifications/authoritative/**`; or any other file that defines a protection mechanism. CI cannot prove that its own check definition was not weakened by the pull request it is checking, and this ADR does not claim that it can. For such pull requests the authoritative review signal is the platform's _Files changed_ view of the actual diff together with the engineering authority's human inspection of it before merging. The standing rule that agents may not self-authorize a governance exception (AGENTS §3; CLAUDE.md §3) is unchanged, and a required check reports when a pull request touches any of these paths so that the engineering authority sees it.

**What the evidence check verifies (review finding F3) `[C]`.** For a pull request that touches `docs/specifications/authoritative/**`, the check passes only if all of the following hold at the pull request's head commit:

1. the change record cited by the revision (a `docs/decisions/CR-*.md` file naming the affected origin tags, 16 §6.7) exists at the head commit. It may predate the pull request; it does not have to be created in the same change set;
2. that change record is in a human-decided, change-authorizing final state recognized by the existing governance contract. This includes `ACCEPTED` (AIW §10), and documented `RESOLVED` records that have been human-decided and reconciled in Reconciliation Report §7 (as the existing records CR-1, CR-2, CR-3, CR-3-F1 and CR-5 are). `REJECTED`, `WITHDRAWN`, draft, open, pending or otherwise non-final records do not constitute authorization evidence. No new state is invented and no existing state is redefined;
3. the matching Reconciliation Report §7 register row exists and identifies the human decider;
4. where the revision supersedes an earlier passage, the Reconciliation Report §6.4 errata row is present (16 §6.7);
5. the artifact revision bump and header revision note are present.

The check validates evidence; it does not authorize. There is no bypass label, skip keyword or self-authorizable exception. Final authorization is the engineering authority's human review and merge decision (E4, E11).

### 6.4 Workflow token and job permissions

- The default workflow token permission is read-only at repository level.
- Every workflow declares `permissions` explicitly, starting from none; each job is granted only what it needs.
- No job receives write permission to repository contents, pull requests, packages or settings. Nothing in tasks 1 and 2 needs it.

### 6.5 Untrusted code in a public repository

- A public repository can be forked, and anyone can open a pull request. All pull-request code — from a fork, or written by an AI tool — is untrusted by CI.
- Running workflows for pull requests from outside contributors requires the engineering authority's approval, at the strictest setting the platform offers.
- Pull-request workflows use the ordinary pull-request trigger. The privileged triggers (`pull_request_target`, and `workflow_run` consuming pull-request output) are prohibited unless a later reviewed decision allows a specific use.
- Fork-triggered workflows receive no secrets and a read-only token (platform behaviour). Since ordinary CI holds no secret at all (6.6), there is nothing for them to reach.

### 6.6 Secrets

- Ordinary CI holds no repository secret of any kind: no production, provider, deployment or migrator credential (Q10; E8). None exists yet, and none is added by this ADR.
- Database credentials used in CI are generated for, and exist only inside, the job's ephemeral containers (S1 §4.10).
- If a later ADR introduces deployment, its credentials are scoped to a context pull-request jobs cannot reach, with short-lived federated credentials preferred. That is for that ADR.
- Logs and artifacts are **publicly readable** in a public repository. They follow S1 §4.10 and §4.11 — no secret values, no resolved configuration dumps, key names only in configuration errors — and are limited to test reports and scan results. Scanner output must never print a detected secret value (AGENTS §9).

### 6.7 Dependencies and third-party CI components

- Dependencies are installed from the frozen lockfile; the job fails if the lockfile would change (S1 §4.13).
- Dependency install scripts do not run unless an exception is explicit and reviewed (S1 §4.8, §4.13).
- Every third-party action is pinned to a full-length commit SHA, and the repository policy enforcing SHA pinning is enabled. Allowed actions are an explicit list; adding one is a reviewed change.
- Container images used by CI jobs are pinned by digest (S1 §4.12).

**Automated dependency proposals (S1 §7 rule 7; E13; review finding F4) `[C]`.** Automated tooling **shall** detect and report: outdated dependencies; vulnerable dependencies; pinned GitHub Actions for which a newer approved version exists; and pinned container or image dependencies where applicable. A report counts as the automated proposal S1 §7 rule 7 requires when it identifies, for each item, the dependency, the currently pinned version, the proposed target, and the relevant vulnerability information where applicable.

_Cadence `[C]`:_ a scheduled run **at least weekly**, plus a run on every pull request for vulnerability findings in the lockfile (the dependency vulnerability scan of S1 §4.13), plus a run whenever the lockfile, the workflow files or the image definitions change. Reports are retained with the ordinary CI artifacts (30 days, E6) and the current report is visible from the CI summary.

_What is not enabled:_ bot-authored commits and bot-authored dependency-update pull requests (E13). Human-approved adoption of a reported update is committed under the engineering authority's Git identity (E17) and reviewed like any other change. No dependency-update or scanner product is selected by this ADR (E5); the product is chosen in task 2 within these requirements.

### 6.8 Secret scanning and the first public push

- A secret scanner runs as a required CI check on every change (Q4; E9). It does not depend on any platform product.
- **Before the repository is first pushed to a public remote**, a full-history secret scan is run locally over every commit on every branch and tag, and its clean result is recorded. Nothing is pushed until that has happened (E8, E9). This makes the scanner the one tool that must be chosen before the remote exists (E5).
- Publication is irreversible in effect: a secret that reaches a public remote is treated as compromised and rotated, whatever is done to the repository afterwards (E8; AGENTS §9).
- A finding is handled under AGENTS §9: location and type are reported; the value is never reproduced.
- The platform's own scanning of public repositories is welcome as defense in depth and is not relied on.

## 12. Risks

1. **One account, two kinds of actor.** The platform cannot show whether the engineering authority or a tool under his account pushed a branch or merged a pull request (6.2). The merge decision being human rests on his review discipline and the tools' prohibition, not on a platform rule. A pull request that changes a check definition can only be judged by reading its diff (6.3).
2. **Publication is permanent.** Anything pushed must be assumed copied. The pre-push history scan is a hard precondition, and making the repository private later undoes nothing.
3. **Public logs.** CI output is world-readable; a careless log line is a disclosure.
4. **Outside pull requests.** Anyone can propose code. Approval before workflow runs, a read-only token and the absence of secrets contain it; they do not make reviewing such pull requests optional.
5. **Third-party actions are a supply-chain surface.** SHA pinning, an allow-list and reviewed updates reduce it. Preferring a short script over an action keeps it small.
6. **Later move to private.** Free-plan branch rules do not follow a personal repository into private visibility (6.11).
7. **The path check validates evidence, not authorship** (6.3). It is a guard against accident, backed by the engineering authority's review at merge.

## 1. Metadata

- Subject: Phase 1 Foundation — the technical platform layer that precedes the Phase 1b walking skeleton and every production module (Arch §35 row "1 Foundation"; DM §33 item 1; AIW §11, §11.1). `[AR]`
- Foundation is **not** one of the 14 DM §4 modules and owns no domain behavior. It owns only the cross-cutting technical primitives the contract itself places outside any single module: the shared `audit` schema and `RecordAuditEvent` library (W1 §7, §8; DM §22 "separate schema"), the operational queue/admission substrate and its reference implementation/tests (DM §6.3; ADR-001), the `TenantTransaction` wrapper and database roles (DM §6.2, §6.4; ADR-012), the table-category registry and its CI gate (DM §6.3), the event envelope / `processed_event` convention / `payload_version` convention "implemented once and reused" (DM §20, §34), the deletion-ledger storage capability/replay hook (DM X11, §27), and the resolver infrastructure — the `cm_resolver` role and the six DM X1 resolver functions, a closed exception to module-schema isolation (DM §6.4 "Ownership and boundary [CR-3]"; ADR-012 and ADR-013 amendments [CR-3]). Logical job rows remain owned by their producing modules. `[AR]`
- Model routing: brief by Fable; review by Codex then a fresh Opus instance (touches ADR-012, ADR-013); human engineer review of ADR-012 work before Phase 1 exits (Rem §1; AGENTS §5). `[AD — process]`

## 3. Scope

In scope (each item traced in §5 and detailed in §6–§15):

1. Repository / Git baseline and CI/CD baseline (Arch §35 Phase 1; AIW §11.1). `[AR]`
2. Fourteen module schemas created empty, plus the separate `audit` schema; no cross-schema FK (DM §4, §22; ADR-013 "Enforcement"; Rem R4). In addition, the `foundation` schema, which holds only the six X1 resolver functions and is not a module schema (DM §6.4 [CR-3-F1]; ADR-013 amendment "Foundation schema [CR-3-F1]"; see item 3a and §9). `[AR]`
3. Database roles `cm_migrator`, `cm_app`, `cm_queue`, `cm_ops_readonly`, `cm_resolver` with grants (DM §6.4; ADR-012 "Database roles" + V1.4 amendment X1). `[AR]`
   3a. Resolver infrastructure as a Foundation-owned Phase 1 platform capability: the `cm_resolver` role and the six resolver functions defined by DM X1 — `resolve_staff_memberships`, `resolve_capability_token`, `resolve_capability_session`, `resolve_invitation`, `resolve_inbound_channel`, `resolve_delivery_by_provider_message` — plus the corresponding architecture/boundary tests (DM §33 item 1; DM §6.4 [CR-3]; ADR-012 amendment "Resolver ownership [CR-3]"). These six functions are a closed, explicit exception to module-schema isolation (ADR-013 amendment [CR-3]); Foundation receives no general access to the Identity or Communication schemas. `identity.resolver_audit` stays Identity-owned; the functions append audit records only through the DM §6.4 SECURITY DEFINER insert. No table permission, grant or schema privilege beyond DM X1 / §6.4 is assumed. `[AR]`
4. `TenantTransaction` wrapper, transaction-local `set_config`, forced fail-closed RLS template, `NOT_FOUND` for cross-tenant ids (DM §6.2, §28; ADR-012; W1 T-1…T-5). `[AR]`
5. `ActorContext` value object and `SystemActor` kinds/purposes as a shared type, consumed only through `TenantTransaction` (DM §5.3; ADR-012 "Tenant context" as amended by "SystemActor purposes [CR-1]"; W1 §3.2; 16 §2.2, §6.4, §7). `[AR]` — construction of STAFF/LEARNER/GUARDIAN contexts is Identity-owned (DM §5 "Owns ActorContext construction") and is **out of scope** here (§7).
6. Table-category registry (five categories) and the CI gate registry-vs-RLS (DM §6.3; ADR-012 amendment X1). `[AR]`
7. Audit foundation: `audit.audit_event`, allow-listed fields, same-transaction write, append-only, sensitive-logging canary (DM §22, §30; W1 §4.6 A-1…A-5; ADR-024 "Audit"). `[AR]`
8. Queue foundation: PostgreSQL-native queue as outbox, enqueue in producer transaction, leases/heartbeat/sweeper, admission tokens, priority classes, failure classes, dead letter, payload contract, `LeaseSweep` (ADR-001; DM §21 header and `LeaseSweep` row; W1 §4.7). `[AR]`
9. Event envelope, `processed_event` convention, payload versioning N/N−1 (DM §20, §34; ADR-023 "Job payload versioning"). `[AR]`
10. Classification-register-driven purge-handler registration gate and the external deletion-ledger storage primitive (DM §27, §34; ADR-006 + amendment X11). The `privacy.classification_register` table itself is Privacy-owned (DM §7.2; ADR-013) — Foundation only provides the CI gate that reads it (§7). `[AR]`
11. Provider boundary rules for object storage: the `StorageProvider` port definition and the architecture/security constraints every adapter must satisfy (tenant-prefixed keys, signed-URL limits, upload validation, no public buckets, write-once capability for the deletion ledger) plus the port-level contract test (ADR-012 "Caches and storage"; ADR-024 "Uploads"; DM §22 payload store; Arch §29, §31). Phase 1 storage capability is limited to what the contract assigns to Phase 1: the deletion-ledger write-once storage primitive (DM §33 item 1). The concrete object-storage adapter is implemented under the approved provider ADR by the module/phase that first needs it; Foundation does not own it. `MalwareScanner` is a port name only — scanning is Content-owned (`ScanUpload`, DM §21) and Foundation owns no scanning implementation or behavior. `[AR]`
12. Secret-handling baseline: managed secret store / KMS envelope access only at adapter/runtime boundary; secret-scan check in CI (ADR-024 "Secrets"; AGENTS §9; AIW §11.1). `[AR]`
13. Observability foundation: span names, attribute allow-list, `tenant_id` + `correlation_id` on every span, Foundations metrics, audit separate from telemetry (DM §27 telemetry contract, §30; ADR-006 "Telemetry and analytics"; W1 §11; Arch §30). `[AR]`
14. Error-code and DTO conventions as shared types: stable codes per DM §28; idempotency-key header convention (DM §28; W1 J-13). `[AR]`
15. Architecture tests and Phase 1 security gates in CI (DM §29 Phase 1 rows; Arch §32 "Continuous from Phase 1"; AGENTS §7). `[AR]`
16. Migration process baseline: expand/contract, additive-only on immutable tables, run as `cm_migrator` in the pipeline before deployment, one-release schema compatibility (ADR-023 "Migrations"; Arch §3 "Migration job", §33). `[AR]`

## 4. Non-goals

- No domain behavior of any module; no Identity tables (including `identity.resolver_audit`), ActorContext construction, `AuthProvider` port, concrete staff IdP adapter, membership/role logic, invitations, capability grants/sessions, OTP (Identity; DM §5.2, §5.5, §6.4 [CR-3], §25.9; ADR-002; ADR-013 amendment [CR-3]; Arch §6). The Arch §35 listing of the staff IdP adapter under Phase 1 is a delivery-phase assignment, not Foundation ownership [CR-3]. `[AR — DM §4 row 1; ADR-013]`
- No organization lifecycle, subscriptions, entitlements, budgets, platform-organization _business_ rules (Tenancy; DM §4 row 3, §6.1; DM A9). `[AR — DM §4 row 3]`
- No consent, deletion requests, retention overrides, classification-register content (Privacy; DM §7; ADR-019). `[AR — DM §4 row 4]`
- No evaluation head, learning projection, delivery, AI, code execution, reporting (Phases 1b–8; Arch §35). `[AR]`
- No stack, framework, ORM, migration tool, test runner, CI platform, hosting, queue library, cloud, secret, storage or observability vendor choice (Cross-ADR Rule 5; AGENTS §3.19; `[UQ]` §17).
- No gate value, retention value, threshold or SLA is decided or hard-coded (AGENTS §3.1, §3.10). `[AR]`
- No "shared services" module: nothing in Foundation may read or write a module's schema; Foundation code is a library and an infrastructure baseline, not a data owner except for `audit` and the OPERATIONAL queue/admission tables named by the contract (§7). The only cross-module reads in Foundation are those performed by the six named X1 resolver functions — a closed exception [CR-3] that is never extended to other queries. `[PR — boundary statement derived from ADR-013 Enforcement, its amendment [CR-3], and W1 §7]`

## 12. Queue / job requirements

- Enqueue in the producer's transaction; if the change rolls back, the job never exists (ADR-001; ADR-013; W1 J-1; AC 23). `[AR]`
- Worker execution rule: claim (queue role) → commit RUNNING + `lease_expires_at` → acquire admission tokens (tenant × work class; provider × account) → provider call outside any DB transaction → new tenant transaction writes result with unique result key → mark complete, release tokens (ADR-001). `[AR]`
- Jobs may run more than once (LOCKED J-6): idempotent handlers (unique result keys, CAS, state guards) → at most one effective domain result; provider idempotency key where supported; no universal exactly-once external delivery (DM §21 header; ADR-001 amendment; W1 J-6; AC 24, 24a, 24b). `[AD — LOCKED]`
- Failure classes INFRASTRUCTURE / RATE_LIMITED / DOMAIN / POISON with behaviors per ADR-001 table; POISON on unknown payload version or tenant/entity mismatch → dead letter immediately + security alert (ADR-001; W1 J-3, J-5; AC 3, 25). `[AR]`
- Leases 5 min with heartbeat for long jobs; sweeper returns expired leases and increments attempts; `LeaseSweep` every 30 s under `cm_queue` (DM §21; ADR-001). Retry defaults: INFRASTRUCTURE exponential 1 s → 5 min, max 8; RATE_LIMITED honours retry-after, ceiling 20 (DM §21 "Default policies"; DM §31-B "job retry parameters" = implementation default). `[AR — PROPOSED DEFAULT]` → `[PR]` config keys `queue.lease_seconds`, `queue.heartbeat`, `queue.retry.infrastructure.{base,max,cap}`, `queue.retry.rate_limited.ceiling`; owner: engineering authority.
- Dead letter after caps; alert when priority ≤ P1; any P0/P1 dead letter pages on-call (DM §30 authoritative over ADR-023 minimum, W1 F-2; J-11). Replay is a platform-operator action that re-validates tenant and payload version and is audited (ADR-001; W1 J-10; AC 28). Dead letters visible only to platform operators (W1 J-9, PROPOSED DEFAULT accepted). `[AR]` Authorization of replay is specified: it is a platform-operator action, audited, performed through the platform operations API and never through tenant sessions (DM §5.4 "Platform operators" [W11 §6, SB-10]; W11 §6 permission row "Dead-letter replay, restore — Platform operator ✓ (audited)"; W11 §6 "platform operators act through the platform operations API, never through tenant sessions (EXISTING, ADR-012, X7)"; W11 OB-4). `[AR]` The replay tool is a Foundation capability. What the sources read do not specify is how platform-operator identity is established and who owns and delivers the platform operations API; Foundation consumes both and defines neither (readiness precondition, §20). `[UQ]`
- Stale jobs complete as no-op, recorded "stale", never an error, never retried (W1 J-7, PROPOSED DEFAULT accepted; AC 26). `[AR — PROPOSED DEFAULT accepted]`
- Priority classes P0 student evaluation, P1 student delivery, P2 teacher AI generation, P3 reports, P4 non-critical; weighted share proposed 50/25/15/7/3 with guaranteed minimum per class (ADR-001; W1 J-8; AC 27). `[AR]` → `[PR]` config key `queue.priority_shares`; owner: engineering authority; proof deferred to the gate-12 benchmark (DM §29 Queue row "Phase 1 / 9 benchmark").
- Admission control table `admission_tokens(scope, key, limit, in_use)`; tokens released on completion or lease expiry (ADR-001); hot-spot risk R1 (Rem §7) included in the benchmark. `[AR]`
- Payload contract: `{payload_version, tenant_id, correlation_id, ids…, idempotency_key}`; no learner content; handlers accept N and N−1; consumers deployed before producers (ADR-001; ADR-023; DM §21; W1 J-2, J-12; AC 29). `[AR]`
- Job state model (behavioral): QUEUED, RUNNING, COMPLETED, DEAD_LETTER, CANCELLED with transitions per W1 §5.6; exact representation is an IMPLEMENTATION DETAIL dependent on gate 12. `[AR]` / `[ID]`
- Organization-status effects on jobs (W1 §4.5, FD-2; DM §6.1): SUSPENDED stops scheduling and new deliveries, marking continues; TERMINATED runs only purge/deletion jobs. Enforced by each owning module's job handlers and write commands on receipt of the Tenancy lifecycle events (DM §19 C32); the queue substrate applies no status filter of its own. `[AR]`
- Queue library: [A-1] `UNRESOLVED — gate 12 (engineering lead) / queue-implementation ADR REQUIRED` (STACK-ADR-001 §4.5, §6 select no queue implementation; the queue ADR follows CR-10 and must also answer which runtime role enqueues job rows and with what grants); the ADR-001 acceptance criteria are the selection contract. `[UQ]`
- Jobs without a tenant — `UNRESOLVED (CR-10, OPEN)`: the envelope texts require `tenant_id` on every job (ADR-001 "Payload contract"; DM §21 header; W1 J-2, J-3; DM §6.5), while `ProcessWebhookEvent` is enqueued before its tenant is resolved, `GateRun` is platform-level and `LeaseSweep` is queue-internal (DM §21 rows).
